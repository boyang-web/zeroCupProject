# 内容接入指南

先看 `src/core/contracts.ts` 的实际契约，本文说明常见修改位置。

2026-11-06：第二、三章已分别拆为morning.ts、noon.ts。Chapter.scenes定义章内地点和通路，hotspot.sprite定义实际图片物件，状态variants定义挪动与换图。不要在章数中增加店内房间。

图片图集登记在sprite-regions.ts；需要重新识别透明区域时运行`python scripts/register-sprites.py`（依赖Pillow）。脚本只读取图像并生成坐标，不修改原PNG。实际显示由AssetImage统一处理；菜单皮肤集中在WoodFrame、wood-theme、wood-ui.css与immersive.css。

## 换对白和故事

背景章位于 `src/content/chapters/arrival.ts`，三店占位内容位于 `shops.ts`，第五章位于 `epilogue.ts`，线索、道具、成就和结局登记在 `src/content/index.ts`。

`shops.ts` 当前用三行种子数据生成相同结构，便于先验证重复模块。正式故事有不同结构时，将每店拆为独立文件，各自导出 Chapter、Dialogue 和 MinigameDefinition；仍在 index 组装，不必继续保留种子生成器。

只改文案或位置不需要改 engine；若改已有 ID，须评估存档兼容性并调整内容版本。

## 加一个观察点

在章节 hotspots 中新增：

```ts
{
  id: 'old-photo', label: '旧照片', x: 35, y: 45, icon: '读',
  completed: { kind: 'clue', id: 'photo-memory' },
  interaction: {
    kind: 'inspect', text: '照片背后有一行小字。',
    action: {
      id: 'read-photo', label: '记下小字',
      effects: [{ kind: 'clue', id: 'photo-memory' }],
    },
  },
}
```

同时在 clues 登记 photo-memory 的标题与回看内容。坐标是当前场景容器的百分比；换构图需重新检查所有热点，尤其窄屏裁切后的对应关系。

## 增加支线任务

在 content.quests 登记稳定 ID、归属 chapterId、标题与说明。章节主任务自动开始；其他任务默认通过剧情 Effect 设置为 active 后才显示，若要进章立即开始，可设置 autoStart。任务结果不必与主线结果相同，出口条件只读取需要的任务。

## 条件与互斥决定

条件直接用于可见性、选项可用性、章节出口和结局。锁住关键路径前，需确认当前分支存在获取条件的办法。

```ts
condition: {
  kind: 'all', conditions: [
    { kind: 'clue', id: 'photo-memory' },
    { kind: 'metric', id: 'listening', min: 2 },
  ],
}
```

同一关键决定的互斥选项使用同一个 decision 名称。不同获取方式若给同一份奖励，使用不同 action id 和同一个 onceKey；重看和重玩不会重复发奖。

## 换图片和模型

1. 把资源放入 public/assets 对应目录。
2. 在 `src/content/assets.ts` 登记 URL、来源与是否占位。
3. 章节只引用资产 ID；构图改变时重定热点位置。
4. 类型检查、内容检查、构建通过后，实测场景裁切与加载失败情况。

当前 GLB 样本位于 placeholders/celadon-set.glb。ObjectStage 接收可选 modelUrl；正式接入前明确尺寸与原点，不能默认任意模型都适合现有相机。渲染方式变化时先替换 presentation，保留 gameplay 的完成结果契约。

## 换或新增小游戏

1. 新增 Vue 组件，接收 `MinigameProps`。
2. 操作结束只发出 `finish`：

```ts
emit('finish', { status: 'completed', score: 85, assisted: false });
// 或 emit('finish', { status: 'cancelled' });
```

3. 在 registry 注册延迟加载函数；配置中填写对应 module。
4. 在 MinigameDefinition.reward 指定一次性剧情效果。小游戏内部不能自行加属性或道具。
5. 外部关闭、加载失败、取消、重试、重复完成都应安全；需要动画或资源的模块必须释放自己的监听、定时器和 GPU 资源。

分数约定为 0–100。实际成功目标由小游戏实现判断；core 只接收有效完成结果，不能凭分数猜测任意玩法的规则。若日后需按品质分级发奖，应明确扩展结果契约并同步存档与测试。

## 增加章节或改变顺序

当前产品要求总共五章，日常迭代优先替换既有章内容。若用户后续明确改变章节范围，可添加 Chapter 并修改 next、firstChapter、出口条件、任务与游戏归属；引擎按数据旅行，无需写死新的章节分支。同步修改当前产品范围校验和存档版本。

## 本轮替换性检查

- 改对白：只改 content。
- 换背景：改资产登记、必要时改热点布局。
- 加支线观察：新增热点、线索与条件，不改存档字段。
- 换物件玩法：新增组件与注册，保留统一结果。
- 增加全新状态语义：改 contracts、engine、存档校验及测试；这不属于只换内容。
